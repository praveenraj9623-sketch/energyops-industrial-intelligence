# Phase 2 ingestion and reconciliation

`scripts/load_postgres.py` resolves the source path from `--source`, `ENERGYOPS_SOURCE_CSV`, or `data/raw/Steel_industry_data.csv`. It compares the CSV SHA-256 with the saved Phase 1 profile **before** opening an ingestion run. CSV records are read one at a time; typed accepted rows and rejected source payloads are written in batches of 1,000 in one database transaction. The audit row is created first. A failed load rolls back all business rows and rejections from that attempt, then marks the audit row failed with only a safe error class. A successful load records source, accepted, rejected, inserted and duplicate counts.

Invalid rows retain their original JSON payload, source row number and all validation reasons in `raw.steel_energy_rejections`. The loader rejects malformed timestamps, off-grid times, invalid or negative numeric values, out-of-range power factors/NSM, unexpected categories, inconsistent day/week/NSM labels and duplicate timestamps. The real CSV is expected to have zero rejections. Values are converted with Python `Decimal` and stored in PostgreSQL `NUMERIC` without rounding. CO₂ remains `co2_value` with unverified unit. Timestamps are stored as `TIMESTAMP WITHOUT TIME ZONE`; `source_timezone_status` is `unspecified`, with no UTC conversion.

A completed run with the same checksum causes a new `skipped_duplicate` audit row and zero new raw rows. For a new checksum, a timestamp already in raw is rejected with an explicit duplicate reason. The unique timestamp and `(checksum,row)` constraints are the final database safeguards. Do not treat a changed file as an append to this single-year source without reviewing its lineage and grain.

`scripts/verify_phase2.py` independently sums the CSV in Python and compares it with SQL aggregates, category counts, timestamps, staging consistency flags, audit counts and the second-run result. It writes `evidence/phase2_reconciliation.json` after the database is available. `NUMERIC` sums are compared with an absolute tolerance of `0.000001` in source units; no floating-point conversion is used for the comparison. Verification fails on any mismatch. Staging derives calendar fields from local timestamps and exposes three consistency flags without changing source values.
